# 운영 성능 기준선

> 아래 수치는 **2026-07-13 성능 개선 작업 시점**에 측정한 값입니다. 이후 업무지시·보관함·업무보고 검토·최근 활동 기능이 추가되었으므로, 지금 값과 그대로 비교하지 말고 **재측정한 뒤 비교**하세요. 코드 수준 회귀는 `npm run test:performance`가 자동으로 막습니다.

## 서울 이전 전/후 (2026-07-30)

앱을 Railway 싱가포르 → **Cloud Run 서울**(`asia-northeast3`)로 옮겼습니다.
같은 브라우저·같은 계정으로, 로그인 상태 RSC 응답을 화면당 8~10회 측정한 **min / avg** 입니다.

| 화면 | Railway 싱가포르 | Cloud Run 서울 |
|---|---|---|
| 대시보드 | 313 / 958ms | 140 / 228ms |
| 근태 | 377 / 484ms | 130 / 138ms |
| 할일 | 313 / 366ms | 142 / 163ms |
| 업무 타임라인 | 740 / 766ms | 209 / 328ms |
| 채팅 | 449 / 584ms | 205 / 273ms |

연결 재사용 `/api/health`: Cloudflare→싱가포르 110~120ms, **Cloudflare→서울 84~86ms**,
서울 직접 12~16ms(= Cloudflare 가 이 회선에서 홍콩을 경유해 약 70ms 를 씁니다).

**유휴 뒤 첫 진입**은 별개입니다. 10분 이상 아무도 쓰지 않으면 `middleware.getUser` 가
300~700ms 로 부풉니다(Supabase HTTPS 연결이 식음). CPU 상시 할당이던 리비전에서도
같은 값이 찍혔으므로 과금 방식과 무관합니다. `/api/keepalive` + Cloud Scheduler 로
720ms → 387ms 까지 줄였습니다. 더 파려면 undici 기본 `keepAliveTimeout`(4초)을 보세요.

구성·비용은 `docs/operations/cloud-run-seoul.md`.

## 반복 가능한 브라우저 확인 시나리오

1. 새 브라우저 프로필에서 포털 로그인 화면을 열고, 대시보드로 이동할 수 있는 승인된 테스트 계정으로 로그인합니다.
2. 대시보드 첫 화면이 안정화될 때까지 기다린 뒤 개발자 도구의 Network에서 초기 문서와 JavaScript 전송량을 확인합니다.
3. 인플루언서 화면을 처음 열고, 콜드 로드 전송량과 JavaScript 전송량을 기록합니다. 초기 그래프에 XLSX 청크가 포함되지 않는지 확인합니다.
4. 업무와 일정 화면을 각각 처음 열고, 화면을 마운트한 직후 반복 새로고침 요청이나 전역 사전 로드 요청이 없는지 확인합니다.
5. 같은 시나리오를 캐시를 비운 새 브라우저 프로필에서 다시 실행하고, 결과는 집계 수치로만 기록합니다.

## 자동 점검

빌드 후 아래 명령으로 각 라우트의 초기 JavaScript 크기, 라우트 예산, 인플루언서 초기 XLSX 그래프, 정적 회귀 보호 규칙을 검사합니다.

```bash
npm run perf:audit
npm run test:performance
```
