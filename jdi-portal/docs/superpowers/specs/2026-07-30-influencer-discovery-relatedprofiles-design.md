# 홈리빙 인플루언서 후보 발굴 (유사 계정 확장) 설계

- 날짜: 2026-07-30
- 도메인: 없음 (독립 스크립트 `jdi-portal/scripts/`). 운영 DB·앱 코드는 건드리지 않는다.
- 상태: 설계 승인 대기
- 관련 마이그레이션: `114`~`116` — **마이그레이션 기록만 있고 테이블은 운영 DB에 존재하지 않는다**
  (2026-07-30 실측: `relation "public.influencer_candidates" does not exist`).
  **2026-08-03 재확인**: `information_schema.tables` 에서 `influencer_candidate%` 조회 결과 **0건**.
  저장소 `supabase/CLAUDE.md`의 "DB 구조만 운영에 남아 있는 상태" 서술은 사실과 달랐고,
  같은 날 "테이블 없음 확정"으로 정정했다.
  파일럿은 로컬 파일을 쓰므로 이 사실이 계획을 바꾸지는 않지만, 나중에 DB로 옮길 때는
  **새 번호로 재작성해야 한다** — `114`~`116` 은 번호가 Remote 에 기록돼 있어
  `db push` 가 조용히 건너뛰므로 재적용이 되지 않는다.

## 배경 / 목적

크리스마스 트리 브랜드 TMA가 인플루언서에게 트리를 무료 협찬하고 릴스를 받는다.
지금은 대표가 인스타그램에서 후보를 **직접 하나씩 검색해서** 팔로워와 조회수를 눈으로 확인한다.
후보 1명당 수 분이 걸려 수백 명 규모를 훑는 것이 사실상 불가능하다.

이 발굴 단계를 자동화한다. 목표는 **"홈리빙 카테고리에서, 꾸준히 릴스를 올리고, 조회수도
꾸준히 나오는, 팔로워 7,000 이상인 계정"** 명단을 등급순으로 받는 것이다.

대표는 그 명단을 보고 직접 계정에 들어가 확인한 뒤, 마음에 드는 사람만 따로 리스트업한다.
**즉 이 도구의 산출물은 최종 결정이 아니라 "확인할 순서가 정해진 후보 명단"이다.**

### 이 설계가 과거 작업 위에 서 있다는 점

운영 DB에는 이미 후보 발굴용 테이블 3+1개가 살아 있다 (`114`~`116`).
그런데 **이 테이블을 쓰는 앱 코드는 유실됐다** — `git branch -a`와 전체 검색으로 확인했고,
저장소 `supabase/CLAUDE.md`에도 "이 6개가 만든 테이블을 쓰는 앱 코드는 master에 없습니다"로
기록돼 있다. 마이그레이션만 운영 DB 기록에서 복구된 상태다(커밋 `29010a9`).

코드는 없지만 **마이그레이션 주석에 남은 실패 경험은 그대로 쓸 수 있다.** 이 설계는 그것을
재사용한다.

| 과거에 배운 것 | 출처 | 이 설계에서 |
|---|---|---|
| 해시태그 "최신 게시물" 피드는 구조적으로 작은 계정만 나온다. 팔로워 많은 크리에이터는 해시태그에 의존하지 않는다 | `116` 주석 | 해시태그 경로를 **쓰지 않는다** |
| 대안은 `relatedProfiles`(인스타 추천 계정) 씨앗 확장. Apify 추가 호출이 없어 비용 증가 0 | `116` 주석 | **주 발굴 경로로 채택** |
| 조회수 평균은 단발 바이럴 하나에 끌려간다 (가구 매장이 48배로 1위) | `116` 주석 | 평균 대신 **중앙값** |
| 가구점·커튼집 같은 **업체 계정**이 다수 섞인다 | `115` 주석 | 업체 자동 제외 규칙 |
| 걸러낸 계정도 기록은 남겨야 한다 — 지우면 다음 실행에 재수집되어 Apify 비용을 또 낸다 | `115` 주석 | 상태 파일에 제외분도 보존 |
| 팔로워 하한 7,000 / 상한 300,000, 릴스 비중 30%, 효율 0.3배, 참여율 구간별 하한, 30일 내 활동 | `116` | 판정 기준 계승. **단 참여율 상한(ER>30 제외)은 폐기** — 실측 데이터가 반박 |

`APIFY_API_TOKEN`은 `jdi-portal/.env.local`에 이미 있다(46자). 새 계정·새 결제 설정이 필요 없다.

| 항목 | 결정 |
|---|---|

| 상태 저장 | **로컬 JSON 파일** (파일럿). 운영 DB 연결은 파일럿 검증 후 별도 판단 |

## 아키텍처

한 파일에 다 넣지 않는다. **Apify를 호출하는 부분과 계산하는 부분을 분리**해야
테스트가 가능하다 (계산 부분은 네트워크 없이 고정 샘플로 검증).

```
jdi-portal/scripts/influencer-discovery/
├─ run.mjs           진입점. 인자 파싱 → 루프 → 보고서 출력
├─ apify.mjs         Apify 호출만. 실패·재시도·빈응답 처리
├─ metrics.mjs       순수 계산: 중앙값, 변동계수, 업로드 간격, 참여율
├─ verdict.mjs       순수 판정: 자동 제외 사유, 업체 판정, 카테고리 적합성
├─ score.mjs         순수 점수·등급 산정
├─ state.mjs         로컬 JSON 읽기/쓰기
└─ report.mjs        마크다운 표 생성
```

`metrics/verdict/score`는 **입력을 받아 값을 반환하는 순수 함수만** 둔다. 네트워크·파일 접근
없음. 이것이 테스트 가능성의 핵심이고, 판정 기준을 나중에 조정할 때 안전하게 바꿀 수 있는 이유다.

### Apify 호출

기존 `influencer-extract`에서 검증된 조합을 그대로 쓴다. 주석에 "`usernames`는 빈 응답
반환 사례 발견"이 남아 있어 `directUrls` + `details`를 쓴다.

```js
POST https://api.apify.com/v2/acts/apify~instagram-scraper/run-sync-get-dataset-items?token=...
{
  "directUrls": ["https://www.instagram.com/<username>/"],
  "resultsType": "details",
  "resultsLimit": 24,
  "searchType": "user",
  "addParentData": false
}
```

응답 형식이 두 가지로 올 수 있다 (기존 코드가 이미 겪은 문제). 첫 항목에 `followersCount`/
`biography`/`latestPosts`/`profilePicUrl` 중 하나가 있으면 프로필 형식, 없으면 게시물 배열
형식으로 보고 `owner*` 필드에서 메타를 복원한다. **이 분기를 그대로 가져온다.**

## 판정 기준

### 1단계 — 자동 제외 (먼저 걸린 사유가 기록된다)

과거 `qualityVerdict()`의 우선순위를 계승하고, 업체 판정을 추가한다.

| 순서 | 사유 | 조건 |
|---|---|---|
| ① | 비공개 계정 | `private === true` |
| ② | 팔로워 7,000명 미만 | `followers < 7000` 또는 null |
| ③ | 팔로워 30만명 초과 | `followers > 300000` |
| ④ | 업체·판매 계정 | 아래 업체 판정 규칙 |
| ⑤ | 릴스 비중 30% 미만 | `reelsRatio < 0.3` 또는 null |
| ⑥ | 릴스 조회수 확인 불가 | 조회수 보이는 릴스가 0개 |
| ⑦ | 릴스 도달 부족 | `efficiency < 0.3` (조회수 중앙값이 팔로워의 0.3배 미만) |
| ⑧ | ~~참여율 이상치~~ | **이 규칙은 폐기한다** — 아래 참조 |
| ⑨ | 참여율 부족 | 7천~1만 미만: <3% / 1만~10만: <2% / 10만+: <1.5% |
| ⑩ | 30일 이상 미게시 | `lastPostAt < now - 30일` 또는 null |
| ⑪ | 카테고리 이탈 | 홈리빙 키워드 0개 (아래 표류 방지) |

### 폐기: 참여율 상한 규칙 (기존 ⑧)

`116`은 `engagementRate > 30`을 "품앗이·소통 계정"으로 보고 자동 제외했다.
**대표가 이미 모아둔 52개 계정 실측 데이터가 이 규칙을 반박한다.**

| 계정 | 팔로워 | ER | 포털 등급 |
|---|---|---|---|
| `hippo.mansion` | 26,050 | 96.8% | S |
| `kkom.bam` | 30,944 | 48.8% | S |
| `konjac.__` | 2,008 | 43.5% | S |
| `yoki.home` | 1,211 | 31.4% | S |

기존 규칙을 쓰면 **이 넷이 전부 자동 제외된다.** 그런데 소개글을 보면 넷 다 릴스 중심
크리에이터다(`konjac.__`은 "비정기 머릿속 상영회", `kkom.bam`은 "#릴스토리를 올려요").

원인은 ER 정의에 있다. ER은 `좋아요÷팔로워`인데 **릴스는 팔로워 밖으로 퍼지기 때문에
좋아요가 팔로워 수를 넘을 수 있다.** ER 100%는 부정이 아니라 릴스가 잘 터진다는 뜻이다.
`116`의 상한은 피드 게시물을 전제로 만들어진 기준이고, **우리가 찾는 대상(릴스 크리에이터)에
정확히 역효과를 낸다.**

대신 진짜 품앗이 신호를 쓴다. 아래 둘 다 만족할 때만 제외한다.
1. `followsCount > followersCount` (팔로잉이 팔로워보다 많음)
2. `followers < 10000`

ER이 30%를 넘는 계정은 제외하지 않고 **보고서에서 가점 요소로 다룬다.**

### 업체 판정 규칙 (④)

과거에 "가구점·커튼집이 다수 섞인다"고 기록된 문제. 단일 신호로 판정하면 오탐이 크다 —
인플루언서도 소개글에 "문의 DM"을 쓴다. 그래서 **2개 이상 히트일 때만 제외**한다.

신호:
1. `isBusinessAccount === true` (인스타 비즈니스 계정 전환). 단독으로 신호 1개.
   `businessCategoryName`의 가능한 값 목록을 확정할 수 없어 카테고리 문자열로 판정하지 않는다.
   대신 값이 있으면 보고서 `비고`에 그대로 노출해 대표가 읽게 한다.
2. 소개글 키워드: `판매|대여|렌탈|주문|예약|구매|배송|택배|공구|공동구매|입금|계좌|사업자|본점|지점|매장|스토어|store|shop|smartstore|납품|시공|설치|견적`
3. 소개글에 스마트스토어·네이버쇼핑·쿠팡 링크
4. 계정명·이름에 `공방|가구|조명|커튼|인테리어시공|스튜디오|official`

2개 이상 → `업체·판매 계정`으로 제외. 1개 → 통과시키되 보고서에 `업체?` 표시를 달아
대표가 눈으로 최종 판단한다. **자동 판정이 애매할 때는 지우지 말고 표시만 한다.**

### 카테고리 표류 방지 (⑪)

유사 계정을 계속 타고 가면 홈리빙에서 벗어난다(육아 → 뷰티 → 여행). 그래서:

- 소개글 + 최근 게시물 해시태그에서 홈리빙 키워드를 센다:
  `인테리어|홈스타일링|집꾸미기|홈데코|홈카페|살림|정리수납|가구|소품|홈파티|셀프인테리어|신혼집|우리집|집들이|리빙|플랜테리어|크리스마스|트리`
- **0개면 제외**하고, 그 계정의 `relatedProfiles`는 **씨앗 큐에 넣지 않는다.**
  → 표류한 가지가 더 뻗지 못하게 잘라낸다.
- 3개 이상이면 씨앗 우선순위를 높인다.

## 꾸준함 계산 (이번에 새로 만드는 부분)

`latestPosts` 24개 중 릴스(`productType === 'clips'` 또는 `type === 'Video'`)만 추린다.

| 지표 | 계산 | 의도 |
|---|---|---|
| `medianViews` | 조회수 보이는 릴스들의 **중앙값** | 단발 바이럴에 안 흔들림 |
| `efficiency` | `medianViews / followers` | 1 넘으면 팔로워 밖으로 퍼진다 |
| `viewCV` | `표준편차 / 평균` (변동계수) | **낮을수록 조회수가 꾸준** |
| `postIntervalDays` | 릴스 게시 간격들의 **중앙값** | 평균은 긴 공백 하나에 끌려감 |
| `reelsRatio` | 릴스 수 / 전체 게시물 수 | 영상 크리에이터 요건 |
| `engagementRate` | `(평균좋아요 + 평균댓글) / 팔로워 × 100` | 기존 정의 계승 |

**표본 부족 처리**: 조회수 보이는 릴스가 3개 미만이면 `viewCV`를 신뢰할 수 없다.
이때는 안정성 항목을 빼고 **나머지 75점을 100점으로 환산**하고, 보고서에 `표본부족` 표시를
단다. 조용히 0점 처리하면 좋은 계정이 억울하게 밀린다.

## 점수와 등급

100점 만점, 네 항목 25점씩. 어느 하나가 압도하지 않게 균등 배분한다.

| 항목 | 25점 | 15점 | 8점 | 0점 |
|---|---|---|---|---|
| 조회수 체급 `medianViews` | 50,000+ | 20,000+ | 5,000+ | 5,000 미만 |
| 효율 `efficiency` | 2.0+ | 1.0+ | 0.5+ | 0.3~0.5 |
| 업로드 꾸준함 `postIntervalDays` | 7일 이하 | 14일 이하 | 21일 이하 | 21일 초과 |
| 조회수 안정성 `viewCV` | 0.5 이하 | 0.8 이하 | 1.2 이하 | 1.2 초과 |

구간 사이는 선형 보간한다(계단식이면 1 차이로 등급이 튄다).

| 등급 | 점수 | 의미 |
|---|---|---|
| S | 80+ | 최우선 컨택 |
| A | 65~79 | 컨택 추천 |
| B | 50~64 | 예비 |

## 산출물 — 채팅 보고 형식

등급순 → 점수순 정렬. 컬럼은 대표가 "들어가서 확인할지" 판단하는 데 필요한 것만 둔다.

| 등급 | 계정 | 팔로워 | 조회수(중앙) | 효율 | 업로드주기 | 안정성 | 최근 | 비고 |
|---|---|---|---|---|---|---|---|---|
| S | [@example](https://www.instagram.com/example/) | 24,300 | 68,000 | 2.8배 | 5일 | 안정 | 2일 전 | |
| A | [@example2](https://www.instagram.com/example2/) | 9,100 | 12,400 | 1.4배 | 11일 | 보통 | 8일 전 | 업체? |

- `안정성`은 숫자(`viewCV`) 대신 말로 표기. 대표가 읽을 수 있어야 한다.
  **안정 = `viewCV` 0.5 이하 / 보통 = 0.8 이하 / 들쭉날쭉 = 0.8 초과.**
- `비고`에 `업체?`, `표본부족`, `businessCategoryName` 값(있으면) 표시.
- 표 아래에 **연락처**를 별도 목록으로 붙인다. 표에 넣으면 너무 넓어진다. 추출 방법:
  - 이메일: 소개글에서 `[\w.+-]+@[\w-]+\.[\w.]+` 매칭 (첫 번째만)
  - 카카오: `카톡|카카오|kakao` 뒤에 오는 아이디 토큰
  - 링크: `externalUrl` 그대로
  - 하나도 없으면 `DM`으로 표기
- 표 끝에 이번 실행 요약: 수집 N건 / 통과 N건 / 제외 사유별 집계 / 씨앗 큐 잔량 / 예상 비용.

## 오류 처리

| 상황 | 처리 |
|---|---|
| Apify 429·5xx | 지수 백오프 3회 재시도. 그래도 실패하면 그 계정만 `error`로 기록하고 다음 계정 진행 |
| Apify 빈 응답 | `error: empty` 기록. 씨앗은 `consumedAt`을 찍어 무한 재시도 방지 |
| 응답이 게시물 배열 형식 | `owner*` 필드로 메타 복원 (기존 코드 분기 계승) |

| 상태 파일 손상 | 실행 중단하고 사용자에게 알림. **덮어쓰지 않는다.** 매 실행 전 `state.backup.json` 생성 |
| 토큰 없음 | 즉시 중단 + 안내 |

## 비용 관리

Apify는 실행량 과금이라 무심코 돌리면 비용이 샌다. 안전장치를 코드에 박는다.

- `--limit` 인자 **필수**. 기본 50, **하드 상한 300** (초과 요청은 거부)
- 실행 전 예상 호출 수와 예상 비용을 출력하고 **확인을 받는다** (`--yes`로 생략 가능)
- `runs` 기록에 실행별 호출 수 누적
- 하루 누적 상한 500호출 — 넘으면 거부

**과금 단위는 파일럿에서 실측한다.** `apify/instagram-scraper`는 $1.50/1,000 results인데,
`details` 응답 1건이 1 result인지 게시물 24개가 각각 계산되는지 문서로 확정하지 못했다.
파일럿 50건을 돌린 뒤 Apify 콘솔의 실제 청구액을 확인해 이 문서를 갱신한다.
최악(24배)을 가정해도 50건 = 약 $1.8이라 파일럿 자체는 안전하다.

## 파일럿 결과 (2026-07-30, 30건) — 설계 가정 2개가 깨졌다

30건 수집 성공(실패 0건). 그런데 **26건이 "릴스 도달 부족"으로 탈락**했고, 조사 결과
탈락의 원인은 계정 품질이 아니라 **우리 데이터가 틀렸기 때문**이었다.

### 근본 원인 ① `details` 모드의 조회수는 신뢰할 수 없다 (확정)

같은 계정(`hippo.mansion`)의 같은 릴스를 두 방식으로 받아 비교했다.

| 릴스 | `apify~instagram-scraper` details 의 `videoViewCount` | `apify~instagram-reel-scraper` 의 `videoPlayCount` | 좋아요 |
|---|---|---|---|
| 바이럴 | 4,173,705 | 8,930,833 | 489,232 |
| A | 4,088 | 371,936 | 4,580 |
| B | 758 | 71,378 | 379 |
| C | 498 | 5,877 | 26 |

`details` 값은 실제의 **10~90분의 1**이다. 결정적 증거: `details` 에서 좋아요 4,580 ·
**댓글 13,659** 인 릴스의 조회수가 4,088 로 나왔다 — 조회수가 댓글보다 적은 것은 불가능하다.
전용 릴스 액터는 12건 모두 `조회수 > 좋아요` 를 만족했다.

`hippo.mansion` 재계산: 효율 **0.13배 → 1.43배**. 탈락이 아니라 통과다.

**→ 설계의 비용 절감 전제("details 1회 호출로 조회수까지 다 얻는다")는 무효다.**
조회수는 `apify/instagram-reel-scraper` 로 따로 받아야 한다. 계정당 호출이 1회 → 2회로
늘지만, 릴스 액터는 $1.00/1k 이라 계정당 약 $0.012 추가에 그친다.

### 근본 원인 ② `relatedProfiles` 가 거의 오지 않는다 (확정)

`116` 주석은 relatedProfiles 를 추가 비용 없는 확장 경로로 전제했다. 실측은 다르다.

- 30개 계정 중 **6개만** relatedProfiles 를 반환했다 (24개는 빈 배열)
- 총 수확 **37개**. 설계가 가정한 "계정당 약 20개 → 약 600개"의 **6%**
- `hippo.mansion` 은 `relatedProfiles: 0`

**→ 눈덩이가 굴러가지 않는다. 발굴 경로 자체를 다시 정해야 한다.**
이것은 패치로 덮을 문제가 아니라 아키텍처 결정이므로 대표와 논의한 뒤 정한다.

### 부수 발견 — 참여율도 중앙값을 써야 한다

`hippo.mansion` 의 ER 이 122% 로 계산됐다. 좋아요 **평균**을 쓰기 때문에 바이럴 1건
(좋아요 489,232)이 12건 평균을 끌어올린 결과다. 조회수에 중앙값을 쓴 것과 같은 이유로
**ER 도 좋아요·댓글의 중앙값으로 바꿔야 한다.** (`influencer-extract` 의 기존 ER 계산도
같은 문제를 안고 있다 — 포털 등급이 부풀려져 있을 수 있다.)

### 근본 원인 ③ ER 하한 게이트는 릴스 크리에이터를 역으로 걸러낸다 (확정, 폐기)

조회수를 고친 뒤 재판정하니 탈락 1위가 **"참여율 부족" 14건**으로 바뀌었다.
그 14건의 실제 도달력을 보면 게이트가 틀렸다는 게 드러난다 — **13건이 효율 0.5배 이상.**

| 계정 | 효율 | 조회수 중앙값 | 업로드 주기 | ER |
|---|---|---|---|---|
| `_favorite.zip` | 4.88배 | 205,261 | 2.6일 | 1.71% |
| `onyu_haus` | 5.24배 | 39,404 | 2.0일 | 2.30% |
| `oneroom_couple` | 4.02배 | 93,368 | 2.0일 | 1.66% |
| `hippo.mansion` | 1.45배 | 50,864 | 1.8일 | 0.86% |

대표가 요구한 조건("꾸준히 올리고 조회수도 꾸준히")에 **가장 잘 맞는 계정들이 탈락**하고 있었다.

원인은 ER 정의다. `ER = 좋아요 ÷ 팔로워` 인데 릴스는 팔로워 밖으로 퍼지므로
**좋아요는 조회수 대비 0.5% 수준이 정상**이고, 팔로워 대비로 환산하면 1~2%에 머문다.
`116` 의 하한(3%/2%/1.5%)은 피드 게시물 기준으로 잡힌 값이다.

**→ ER 하한 게이트를 폐기한다.** 도달 실패는 효율 0.3배 하한이 더 직접적으로 걸러낸다.
대신 `좋아요 중앙값 ÷ 조회수 중앙값 < 0.2%` 이면 `반응낮음` 플래그로 **표시만** 한다
(조회수 부풀림 의심 계정을 사람이 판단하도록).

`116` 에서 계승한 참여율 규칙 **상한·하한이 모두 폐기**됐다. 릴스 크리에이터를 찾는
목적에는 ER 자체가 부적합한 지표라는 결론이다. ER 은 참고 수치로만 남긴다.

### 파일럿 비용

Apify API 로 조회한 **실제 청구액** (`scripts/influencer-discovery/cost.mjs`):

| 액터 | 실행 | 실제 비용 | 평균/회 |
|---|---|---|---|
| `apify/instagram-reel-scraper` (릴스 12건) | 31회 | $0.9982 | **$0.0322** |
| `apify/instagram-scraper` (details) | 31회 | $0.0837 | **$0.0027** |
| 합계 (오늘) | 62회 | **$1.0819** (약 1,500원) | |

**계정 1개당 실제 단가 $0.0361 (약 50원).**

추정이 크게 틀린 부분: `details` 호출을 최악 $0.036 으로 잡았는데 실제는 **$0.0027** —
13배 과대 추정이었다. 반면 릴스 액터는 $0.028 추정 대비 실제 $0.0322 로 근사했다.
**비용의 92% 가 릴스 액터에서 나온다.**

### 비용 구조에서 나오는 개선 여지

지금 `discover()` 는 모든 계정에 대해 프로필 + 릴스를 **둘 다** 호출한다. 그런데 값싼
프로필 호출($0.0027)만으로 판정 가능한 제외 사유가 여럿이다 — 팔로워 하한·상한,
비공개, 업체, 릴스 비중, 카테고리 이탈. 파일럿 30건 중 9건이 이 단계에서 걸렸다.

**→ 프로필 판정을 먼저 통과한 계정에만 릴스를 호출하면 비용의 약 30% 를 절감한다.**
(30건 기준 $1.08 → 약 $0.75)

### 무료 크레딧 잔량 경고

계정은 **FREE 플랜($5/월 크레딧)** 이고, 이번 결제주기(2026-07-08 ~ 08-07) 누적
**$3.99 로 80% 소진**, 잔액 약 $1.01 이다. 이 중 $2.9 는 포털의 기존
`influencer-extract` 가 52개 계정을 모을 때 쓴 것이다.

잔액 $1.01 = 계정 약 **28개** 분량. 본격 발굴(수백 계정) 전에 플랜 결정이 필요하다.
무료 플랜은 크레딧 초과 시 **다음 주기까지 정지**된다(초과 청구가 아니라 중단).
오프라인 재판정(`--rejudge --offline`)은 저장된 조회수를 재사용해 **비용 0원**이다 —
판정 기준을 바꿀 때마다 재수집하지 않아도 된다.

## 근본 원인 ④ 씨앗을 후보로도 채점했다 — 파일럿 지출이 전액 낭비였다

대표가 지적: "최종 목록이 대부분 이미 내가 등록해놓은 인플루언서던데."

맞다. 씨앗 46개가 **대표가 포털에 이미 등록한 계정**인데, `discover()` 가 그 씨앗을
그대로 후보로도 채점해서 보고했다. 3차 판정의 16건은 **전부 이미 등록된 계정**이었다.

**즉 오늘 쓴 $1.08 로 얻은 새 후보는 0명이다.** 설계 문서에 "씨앗 자격과 후보 자격은
별개"라고 써놓고 코드에서 분리하지 않았다.

### 고친 내용

`state.registered` 를 도입했다. 포털 `influencers` 테이블의 계정 52개를 등록 명단으로
기록하고, 세 지점에서 차단한다.

| 지점 | 동작 |
|---|---|
| `pickPendingSeeds()` | 등록 계정·`sourceOnly` 씨앗을 후보 대기열에서 제외 |
| `discover()` 루프 진입부 | **Apify 호출 전** 차단 — 여기서 걸러야 비용이 0원이다 |
| `collectRow()` | 등급을 통과해도 등록 계정이면 보고서에 넣지 않음 |

등록 계정은 **확장 출발점(`sourceOnly`)으로만** 쓴다. 대소문자·공백을 무시해 판정한다.

### 고친 뒤 재판정 결과 (비용 0원)

```
통과 21건 / 보고 대상 0건
통과했지만 이미 등록돼 제외: 16건
씨앗 큐 잔량: 37개  ← relatedProfiles 로 거둔 진짜 새 계정
```

**보고 0건이 정확한 답이다.** 앞의 16건 보고는 거짓 성과였다.
남은 자산은 relatedProfiles 로 거둔 **미평가 신규 계정 37개**다.

### 추가 지시: 한 번 보고한 계정은 다시 보고하지 않는다

대표 지시사항. 실제로 2차·3차 판정에서 겹치는 계정을 두 번 보고했다 — 버그였다.

`collectRow()` 가 `reportedAt` 을 보고 이미 보고한 계정을 걸러낸다.
**판정 기준이 바뀌어 등급이 올라가도 다시 내보내지 않는다.** 대표가 같은 명단을 두 번
확인하는 낭비를 막는 것이 등급 정확성보다 우선한다.

- 구버전 상태의 `reported === true` 도 "이미 보고함"으로 인정한다(마이그레이션 불필요).
- 전체를 다시 봐야 할 때만 `--all` 로 우회한다. 기본은 항상 신규만.
- 회귀 검사 5개로 고정했다(두 번 보고 금지 / 등급 상승 시에도 금지 / 구버전 형식 /
  `--all` 우회 / 등록 계정은 보고 이력과 무관하게 항상 제외).

`rowFrom`·`collectRow` 는 `report.mjs` 로 옮겼다. `run.mjs` 는 import 하면 `main()` 이
실행되어 테스트에서 불러올 수 없기 때문이다.

### 보고서 형식 변경

**`## 신규 후보 N명` 을 보고서 최상단에 둔다.** 이 도구의 유일한 성과 지표다.
0명일 때는 제외 사유(이미 등록 N건 / 이전에 보고 N건)를 함께 밝혀서,
"아무 일도 안 일어난 것"과 "걸러낸 것"을 구분한다.

### 여기서 얻은 교훈

파일럿 검증 항목에 "**새 후보가 몇 명 나왔는가**"가 없었다. "판정 로직이 도는가"만 봤다.
그래서 3차까지 판정을 고치면서도 산출물이 전부 기존 계정이라는 걸 못 봤다.
**앞으로 실행 보고에는 `신규 후보 수`를 최상단에 둔다.**

## 실전 실행 결과 (2026-07-30)

중복 차단·비용 절감·요리 채널 제외를 모두 적용한 뒤의 실제 발굴 성과.

| 실행 | 대상 | 신규 후보 | 릴스 생략 | 비용 | 계정당 |
|---|---|---|---|---|---|
| 1차 (씨앗=등록계정) | 30 | **0명** | — | $1.08 | 50원 |
| 2차 (신규 씨앗) | 37 | **11명** | 23건 | $0.42 | 15원 |
| 3차 (+요리 제외) | 40 | **4명** | 33건 | $0.27 | **9원** |

**누적 신규 후보 15명.** 계정당 단가가 50원 → 9원으로 떨어진 것은 프로필 선판정이
비싼 릴스 호출을 대부분 막아주기 때문이다(3차에서 40건 중 33건 생략).

### 요리 채널 제외 (대표 지시)

2차 결과에 `honbap.master`(혼밥마스터)·`nomoney_cook` 같은 요리 채널이 섞였다.
원인은 `살림` 키워드가 살림 → 집밥 → 요리로 번진 것.

`살림` 자체는 홈리빙에 유효한 신호(살림템·살림꿀팁)라 빼지 않았다. 대신 `COOKING_RE` 를
두고 **요리 신호가 홈리빙 신호와 같거나 많으면** `카테고리 이탈(요리 채널)` 로 제외한다.
요리 신호가 0이면 무조건 통과시켜, 홈리빙 계정이 음식 얘기를 조금 하는 경우는 살린다.
`홈스토랑` 은 홈리빙 키워드에서 제거했다.

3차 실행에서 **8건**이 이 규칙으로 걸렸다(`momo_kitchen802`, `darimi_unni` 등).

### 예산 한도 안전장치

무료 플랜은 크레딧 초과 시 **다음 주기까지 계정이 정지**된다(초과 청구가 아니라 중단).
그래서 `--max-usd`(기본 $0.50)를 두고, 한도에 닿으면 릴스 호출을 멈추고 해당 씨앗을
**소비 처리하지 않은 채** 남긴다. 다음 실행에서 다시 잡힌다(프로필 $0.0027 만 재지출).

### 크레딧은 포털과 공유된다

`instagram-profile-scraper` 실행 수가 이 작업과 무관하게 5 → 10 으로 늘었다.
포털의 `influencer-extract` 가 **같은 Apify 계정·같은 $5 크레딧**을 쓴다.
포털에서 인플루언서를 등록하면 발굴 예산이 줄어든다. 플랜 결정 시 함께 고려해야 한다.
