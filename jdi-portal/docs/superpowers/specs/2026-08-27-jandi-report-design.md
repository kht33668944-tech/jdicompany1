# 잔디(JANDI) 웹훅 업무 자동 보고 — 설계

- 작성일: 2026-08-27
- 상태: 설계 승인 대기
- 관련 문서: `docs/operations/cloud-run-seoul.md`(Cloud Scheduler 운영), `../CLAUDE.md`(성능 불변조건)

## 1. 배경과 목표

포털에 쌓이는 업무·업무보고·검토·일정 정보를 확인하려면 직원이 직접 대시보드에
들어가야 한다. 잔디는 이미 전 직원이 상시 켜 두는 도구이므로, **하루 두 번 포털
현황을 잔디 채널로 자동 게시**해 "들어가 봐야 아는" 상태를 없앤다.

성공 기준:

1. 평일 오후 1시와 오후 6시에 사람이 아무것도 하지 않아도 잔디에 보고가 올라온다.
2. 보고서만 읽고도 **누가 무엇을 했고, 무엇이 밀렸는지** 알 수 있다.
3. 운영 비용이 늘지 않는다(외부 유료 API 미사용).
4. 포털 본체의 속도와 안정성에 영향이 없다.

## 2. 범위

**포함**

- 오늘 일정
- 업무(할일) 현황 — 완료 / 진행중 / 기한 지남
- 업무 타임라인 — 오늘 올라온 업무보고
- 검토 대기 — 아직 처리되지 않은 검토 요청
- 담당자 실명 표기 (팀 전체 1건으로 묶되 사람 이름은 노출)

**제외 (명시적으로 뺀다)**

- 근태(출퇴근·휴가) — 사용자가 불필요하다고 결정
- AI 문장 생성(Claude 등 LLM API) — 비용 발생 및 사실 왜곡 위험
- 개인별 DM 발송 — 채널 1건으로 충분
- 지출·인플루언서 등 나머지 도메인 — 이번 범위 밖 (구조는 블록 추가가 쉽도록 둔다)

## 3. 전체 구조

```
Cloud Scheduler 작업 "jdi-portal-jandi-report"
  cron: 0 13,18 * * 1-5   /  타임존: Asia/Seoul
        │  POST + 헤더 X-Cron-Secret
        ▼
POST /api/cron/jandi-report
        │  1) 비밀키 검증 (틀리면 401, 본문 없음)
        │  2) 팀 전체 보고 데이터 1회 조회
        ▼
src/lib/jandi/queries.ts   → 원시 데이터
src/lib/jandi/format.ts    → 한국어 문장 조립 (순수 함수)
src/lib/jandi/send.ts      → 잔디 웹훅 POST
        ▼
잔디 채널에 보고서 게시
```

Cloud Scheduler는 **작업 3개까지 무료**이고 현재 `jdi-portal-keepalive` 1개만
쓰고 있다. 오후 1시·6시는 `0 13,18 * * 1-5` 한 줄로 표현되므로 **작업 1개만
추가**되어 총 2개 — 무료 범위 안이다.

## 4. 데이터 소스

모두 이미 포털이 읽고 있는 데이터이며, **새 테이블·새 마이그레이션이 없다.**

| 블록 | 출처 | 재사용할 타입 |
|---|---|---|
| 오늘 일정 | `schedules` (`getTodaySchedules` 와 같은 조건) | `ScheduleWithProfile` |
| 업무 현황 | `tasks` + 담당자 | `DashboardTaskSummary` |
| 업무 타임라인 | `work_timeline_entries` 중 오늘 작성분 | `WorkTimelineEntry` |
| 검토 대기 | `work_timeline_reviews` 중 미처리 건 | `PendingReviewItem` |

**중요 — 대시보드 조회 함수를 그대로 부르지 않는다.** 대시보드의
`DashboardSnapshot` 경로는 `DashboardSnapshotContext`(`userName`,
`canViewCompanyWork`)에 묶인 **개인 시야**다. 보고서는 팀 전체 시야가 필요하므로
`src/lib/jandi/queries.ts` 에 **별도 조회**를 두고, 위 표의 **타입만 재사용**한다.

이렇게 나누면 부수 효과로 저장소 규칙 하나를 자동으로 지킨다: 대시보드 초기
데이터(빠른 경로 + RPC 폴백 양쪽을 함께 고쳐야 하는 영역)를 건드리지 않으므로
`npm run test:performance` 의 쌍(pair) 검사에 걸리지 않는다.

조회는 `src/lib/db/postgres.ts` 의 pg 풀을 쓰되, 풀이 죽어 있으면
(`markPostgresUnavailable` 상태) Supabase service role 클라이언트로 우회한다.
이는 포털의 기존 이중 데이터 접근 패턴과 같다.

KST 기준일은 `(NOW() AT TIME ZONE 'Asia/Seoul')::DATE` 로 계산한다.

## 5. 두 슬롯의 내용 차이

| | `noon` (13:00) | `evening` (18:00) |
|---|---|---|
| 제목 | 📋 JDI 점심 현황 | 📋 JDI 하루 마감 |
| 관점 | **앞으로 할 일** | **오늘 한 일** |
| 오늘 일정 | 남은 일정만 (현재 시각 이후) | 전체 일정 |
| 업무 | 진행중 + 기한 지남 | 오늘 완료 + 진행중 + 기한 지남 |
| 업무보고 | 생략 | 오늘 올라온 업무보고 |
| 검토 대기 | 포함 | 포함 |

슬롯은 **서버 시각(KST)으로 스스로 판정**한다 — 15시 이전이면 `noon`, 이후면
`evening`. 그래야 Cloud Scheduler 작업이 1개로 유지된다(§12). 수동 테스트용으로
`?slot=noon|evening` 쿼리로 덮어쓸 수 있고, 그 외의 값이 오면 400을 반환한다.

## 6. 메시지 형식

잔디 incoming webhook 규격으로 전송한다.

- `POST <JANDI_WEBHOOK_URL>`
- 헤더: `Content-Type: application/json`,
  `Accept: application/vnd.tosslab.jandi-v2+json`
- 본문: `{ body, connectColor, connectInfo: [{ title, description }] }`

`body` 에 제목 줄, `connectInfo` 각 항목에 블록 하나를 담는다.
`connectColor` 는 지연 건이 있으면 경고색, 없으면 기본색으로 둔다.

> 구현 첫 단계에서 이 규격을 실제 웹훅으로 1회 스모크 테스트해 확인한다.
> 규격이 다르면 `send.ts` 한 파일만 고치면 되도록 전송을 분리해 둔 것이다.

### 출력 예시 (evening)

```
📋 JDI 하루 마감 · 8월 27일(수) 18:00

✅ 오늘 완료 3건
  · 인플루언서 계약서 발송 — 김효태
  · 8월 지출 정산 — 이OO
  · TMA 시딩 스케줄 확정 — 박OO

🔄 진행 중 5건 (김효태 2 · 이OO 2 · 박OO 1)

⚠️ 기한 지남 1건
  · 광고 소재 3차 검수 — 박OO (2일 지남)

📝 오늘 올라온 업무보고 2건
  · 김효태 — 인플루언서 1차 컨택 결과
  · 이OO — 8월 광고비 집행 내역

👀 검토 대기 2건
  · 김효태 → 이OO : 계약서 문구 확인 (3일째)
  · 박OO → 김효태 : 소재 승인 요청 (오늘)
```

### 표기 규칙

- 목록은 블록당 **최대 5건**, 넘으면 마지막 줄에 `· 외 N건`.
- 해당 블록에 0건이면 **그 블록을 통째로 생략**한다.
- 모든 블록이 0건이면 `오늘은 기록된 활동이 없습니다.` 한 줄만 보낸다.
  (침묵하지 않는다 — 침묵은 장애와 구분되지 않는다.)
- 담당자가 여럿인 업무는 `김효태 외 1명`.
- 담당자 이름이 없으면 `담당자 미지정`.
- 업무 제목이 40자를 넘으면 잘라내고 `…` 을 붙인다.

## 7. 파일 구성

기존 도메인 모듈 패턴(`src/lib/<domain>/`)을 따른다. `activity` 도메인이 쓰는
**"DB에는 사실만, 한국어 문장은 `format.ts` 에서 조립"** 구조를 그대로 채용해,
문구를 바꿀 때 DB나 조회를 건드리지 않아도 되게 한다.

| 파일 | 책임 | 의존 |
|---|---|---|
| `src/lib/jandi/types.ts` | 보고 데이터 타입, 잔디 페이로드 타입, `ReportSlot` | 없음 |
| `src/lib/jandi/queries.ts` | 팀 전체 보고 데이터 1회 조회 | pg 풀 / Supabase |
| `src/lib/jandi/format.ts` | 데이터 → 잔디 페이로드 (**순수 함수, 부수효과 없음**) | `types.ts` |
| `src/lib/jandi/send.ts` | 웹훅 POST, 타임아웃, 재시도, 로깅 | `types.ts` |
| `src/app/api/cron/jandi-report/route.ts` | 비밀키 검증 → 조회 → 조립 → 전송 | 위 4개 |
| `src/lib/supabase/middleware.ts` | `/api/cron/` 를 로그인 리다이렉트 예외에 추가 (1줄) | — |

`format.ts` 가 순수 함수인 것이 이 설계의 핵심이다. 네트워크도 DB도 없이
입력 객체 하나로 출력이 결정되므로, 모든 표기 규칙을 테스트로 고정할 수 있다.

## 8. 보안

- **웹훅 URL은 비밀이다.** URL을 아는 사람은 누구나 해당 잔디 채널에 글을 쓸 수
  있다. 코드·문서·깃에 넣지 않고 `JANDI_WEBHOOK_URL` 환경변수로만 주입한다.
  현재 URL은 채팅으로 공유된 이력이 있으므로 **구현 후 잔디에서 재발급**한다.
- 라우트는 `X-Cron-Secret` 헤더가 `CRON_SECRET` 환경변수와 **일치할 때만** 동작한다.
  불일치 시 401을 반환하고 본문에 아무 정보도 담지 않는다. 비교는
  `crypto.timingSafeEqual` 로 한다.
- 미들웨어에서는 `/api/cron/` 를 **로그인 리다이렉트 예외**에만 추가한다.
  **인증 왕복 조기 생략 목록(`/api/health`, `/api/keepalive`)에는 넣지 않는다** —
  그 목록은 1분마다 불리는 경로만을 위한 성능 장치이고, 회귀 테스트가 그 경계를
  고정하고 있다. 이는 `/api/sign/`(전자서명 공개 경로)이 쓰는 방식과 같은 선례다.
- 조회는 RLS를 우회하는 경로를 쓰므로 **전사 공개 채널에만** 보낸다는 전제를 둔다.
  담는 정보는 이름·업무 제목까지만이며, 업무 본문·첨부·링크는 담지 않는다.

## 9. 성능 불변조건 영향

없다. 근거:

- 미들웨어 인증 캐시 로직을 수정하지 않는다(예외 목록에 경로 문자열 1개만 추가).
- keepalive 경로와 `warmup.ts` 를 건드리지 않는다.
- 대시보드 빠른 경로·RPC 폴백을 건드리지 않는다(§4).
- 대시보드 업무 요약 사전 필터를 건드리지 않는다.
- 클라이언트 번들이 늘지 않는다(서버 전용 코드).

구현 후 `npm run test:performance` 로 확인한다.

## 10. 실패 처리

| 상황 | 동작 |
|---|---|
| 비밀키 불일치 | 401, 본문 없음, 서버 로그에만 기록 |
| `slot` 쿼리 값이 이상함 | 400 |
| 환경변수 누락 | 500 + 로그, 잔디 전송 시도 안 함 |
| DB 조회 실패 | 500 + 로그. 잔디에 **오류 메시지를 보내지 않는다**(내부 정보 노출 방지) |
| 잔디 응답 실패/타임아웃 | 최대 2회 재시도(1초, 3초 간격). 그래도 실패면 로그만 남기고 500. 다음 회차에 자연히 복구 |
| Cloud Run 콜드 스타트 | Cloud Scheduler 재시도 설정으로 흡수 |

포털 본체는 이 경로의 실패에 영향받지 않는다 — 독립된 라우트다.

## 11. 테스트 계획

기존 규칙대로 `node:test` 기반, `scripts/*.test.mjs` 로 둔다.

`scripts/jandi-report.test.mjs`:

1. **빈 날** — 모든 블록 0건이면 `오늘은 기록된 활동이 없습니다.` 한 줄만 나온다.
2. **블록 생략** — 검토 대기만 있는 날은 업무 블록이 출력에 없다.
3. **5건 잘림** — 완료 7건이면 5건 + `외 2건` 이 나온다.
4. **담당자 표기** — 담당자 2명이면 `김효태 외 1명`, 0명이면 `담당자 미지정`.
5. **긴 제목** — 40자 초과 제목이 잘리고 `…` 이 붙는다.
6. **슬롯 차이** — 같은 데이터로 `noon` 에는 업무보고 블록이 없고 `evening` 에는 있다.
7. **슬롯 자동 판정** — KST 13시는 `noon`, 18시는 `evening` 으로 판정된다.
8. **지연 색상** — 기한 지남 건이 있으면 `connectColor` 가 경고색이다.

`scripts/jandi-cron-auth.test.mjs`:

9. **비밀키 없음/불일치** → 401이고 응답 본문에 힌트가 없다.
10. **미들웨어 경계** — `/api/cron/` 가 로그인 리다이렉트 예외에는 있고,
    인증 조기 생략 목록에는 **없다**.

`package.json` 에 `test:jandi` 스크립트를 추가한다. 10번은 미들웨어 경계를 이미
검사하는 `test:security` 쪽에 합류시키는 것이 자연스러운지 구현 시 확인하고,
어느 쪽이든 **반드시 한 곳에서는 실행되게** 한다.

## 12. 배포·운영 절차

1. Cloud Run 서비스에 환경변수 2개 추가: `JANDI_WEBHOOK_URL`, `CRON_SECRET`
   (`CRON_SECRET` 은 무작위 32바이트 이상).
2. `master` 병합 → Cloud Build 트리거가 자동 배포.
3. Cloud Scheduler 작업 생성 (프로젝트 `jdi-portal-seoul`):
   - 이름: `jdi-portal-jandi-report`
   - 빈도: `0 13,18 * * 1-5`
   - 타임존: `Asia/Seoul`
   - 대상: HTTP POST `https://<run.app>/api/cron/jandi-report`
   - 헤더: `X-Cron-Secret: <값>`
   - 슬롯은 라우트가 시각으로 판정하므로 쿼리를 붙이지 않는다.
4. 수동 확인: 배포 후 비밀키를 넣어 1회 호출해 잔디에 실제로 뜨는지 본다.
5. 문서 `docs/operations/cloud-run-seoul.md` 의 스케줄러 표에 이 작업을 추가한다.

## 13. 환경변수

| 이름 | 용도 | 비고 |
|---|---|---|
| `JANDI_WEBHOOK_URL` | 잔디 incoming webhook 주소 | 비밀. 노출 시 재발급 |
| `CRON_SECRET` | 스케줄러 인증용 공유 비밀 | 비밀. 32바이트 이상 무작위 |

둘 중 하나라도 없으면 라우트는 500을 반환하고 아무것도 보내지 않는다.

## 14. 확정된 결정 사항

- 실행 주기: **평일(월~금)만**. 주말 보고 없음. 공휴일 판정은 하지 않는다
  (`src/lib/schedule/holidays.ts` 가 있으나, 공휴일에 보고가 한 번 더 가는 것은
  피해가 없으므로 복잡도를 늘리지 않는다).
- 요약 방식: **기계적 집계**. LLM 미사용.
- 보고 단위: **팀 전체 1건**, 항목마다 담당자 실명 표기.
- cron 실행 위치: **Cloud Scheduler** (사용자 PC 아님).
- Scheduler 작업 수: **1개** (§5의 시각 자동 판정으로 달성).
